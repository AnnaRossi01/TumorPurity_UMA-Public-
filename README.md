# Tumor Purity Workflow

This repository contains a reproducible computational workflow for comparing tumor purity estimates derived from multiple orthogonal methods. The public release is intentionally sanitized and focused on the analytical implementation, data-cleaning strategy, and biological rationale behind the project rather than on private patient-level information or local laboratory paths.

## Overview

Tumor purity is a central quantity in cancer genomics because it describes the fraction of tumor cells relative to normal cells in a biological specimen. Accurate estimation of purity affects multiple downstream analyses, including copy-number interpretation, mutation burden estimation, clonal architecture reconstruction, and the reliability of genomic biomarkers.

This project brings together multiple purity estimation strategies:

- flow cytometry-derived purity
- ASCAT.sc-derived purity
- ichorCNA-derived purity
- PureCN-derived purity
- a copy number burden (CNB) analysis to contextualize method performance

The core objective is not only to compare these methods numerically, but to build a transparent and robust workflow that is resistant to common data-quality issues such as missing values, inconsistent sample IDs, duplicate entries, and differences in file structure across tools.

## Why this work matters biologically

Tumor purity is not merely a technical output; it directly impacts biological interpretation.

When purity is misestimated, several downstream conclusions can be distorted:

- copy-number events may appear artificially weak or strong,
- somatic alteration interpretation can become unreliable,
- clonal composition may be inferred incorrectly,
- and apparent genomic instability may reflect assay limitations rather than true biology.

This is especially important in hematologic malignancies and other heterogeneous tumor contexts, where a sample can contain variable proportions of tumor and normal cells and where sequencing coverage may not be sufficient to capture the full genomic landscape. In such settings, a method may fail not because the underlying biology is absent, but because the assay or the model assumptions do not match the biology of the sample.

A major biological motivation in this project is the relationship between genomic instability and signal quality. Tumors with low or sparse copy-number alteration may produce weak signals for purity estimation tools, even if biologically valid. Conversely, tumors with extensive genomic alteration may provide stronger evidence for a reliable purity estimate. This is why the project includes a CNB analysis: to evaluate whether the apparent failure of a method reflects a lack of biologic signal or a technical limitation of the assay.

## Project goals

This repository was built to:

- standardize the data structure across multiple purity-estimation tools,
- compare purity estimates generated by independent methods,
- identify unstable or missing values,
- implement quality control checks before comparison,
- explain discrepancies in terms of biology and assay limitations,
- and provide a reusable computational workflow for future cohorts.

The public version is intentionally method-focused and avoids exposing raw patient-level data, local laboratory paths, or private sequencing metadata.

## Main implementation components

### 1. Snakefile

The `Snakefile` is the workflow entry point. It orchestrates the analysis using Snakemake and defines the sequence of operations required to:

- read the sample manifest,
- map each sample to its BAM/VCF files,
- run ASCAT.sc,
- prepare PureCN assets,
- perform purity estimation,
- compare outputs from multiple tools,
- and generate summary reports and plots.

This makes the workflow reproducible and modular. Each step is explicitly represented as a rule, so the pipeline can be rerun, adapted, or extended for a different cohort.

### 2. Manifest-driven design

The analysis relies on a manifest file that links each sample to the relevant files required by the pipeline:

- sample ID
- BAM path
- VCF path
- ichorCNA result path

This is fundamental for a reusable workflow. By separating data specification from analysis logic, the project can be applied to different cohorts without hardcoding sample-specific values into the scripts.

### 3. purity_comparisonOOP.py

The main implementation is contained in `workflow/scripts/purity_comparisonOOP.py`.

This script handles:

- loading the manifest,
- reading flow cytometry values,
- loading ASCAT.sc outputs,
- loading PureCN outputs,
- loading ichorCNA results,
- normalizing sample identifiers,
- removing duplicates,
- checking for missing or failed values,
- merging all sources into a single comparison table,
- generating summary statistics and visualizations.

This script is the central place where data harmonization and comparison logic are implemented. A large portion of the value in this project is in making heterogeneous data comparable before the actual interpretation begins.

## Data cleaning and harmonization

A substantial part of the real work is not the final reporting step, but the data-cleaning and harmonization required before any method comparison is meaningful.

The implementation includes logic for:

- trimming and standardizing sample IDs,
- normalizing column names,
- checking for duplicate sample entries,
- ensuring required columns are present,
- validating file existence,
- handling missing purity values consistently,
- flagging samples with method-specific failures,
- and generating QC summaries.

Without these steps, comparisons across methods become biased by simple issues such as inconsistent naming, missing files, or sample mismatch between different data sources.

This makes the pipeline not only computationally functional, but scientifically robust.

## Copy number burden analysis

The `CNB_analysis` directory contains a separate analysis workflow designed to evaluate genomic instability for each sample using an orthogonal copy-number approach.

The logic is:

- convert CNVkit output into a standard segmentation format,
- evaluate altered segments using a log2-ratio threshold,
- compute the proportion of the genome affected by copy-number changes,
- classify samples as "Flat" or "Altered" based on a burden threshold,
- and then interpret how this status relates to purity-estimation performance.

This analysis is biologically meaningful because it helps explain why certain samples are difficult to assess with purity tools. If a targeted panel covers only a small part of the genome, the method may have insufficient signal to estimate tumor fraction accurately. By quantifying the overall genomic burden, the project links algorithmic behavior to biological signal availability.

## Expected workflow logic

The analytical pipeline generally follows this sequence:

1. Prepare a manifest with sample identifiers and file references.
2. Validate and standardize the input data.
3. Run ASCAT.sc for each sample.
4. Generate PureCN inputs and reference assets.
5. Run PureCN.
6. Load flow cytometry values.
7. Load ichorCNA values from the manifest.
8. Merge all source-specific estimates by sample ID.
9. Apply quality checks and filtering.
10. Generate summary statistics and plots.
11. Interpret deviations in the context of tumor biology and panel coverage.

This structure keeps the project modular and transparent. The most important analytical work happens before the final comparison, during the data validation and harmonization stages.

This public version avoids exposing local storage layouts while retaining a realistic structure for a user who wants to adapt the workflow to their own dataset.

## Reproducibility

The project is designed to be reproducible and version-controlled. The computational environment is specified in:

- `workflow/envs/python_env.yaml`

The workflow is organized around clearly defined inputs, modular scripts, and explicit file dependencies. This makes it suitable for reuse on similar tumor-purity workflows and for adaptation to new datasets.

## How to navigate the repository

If you are new to the project, the best order is:

1. Read this README.
2. Inspect `Snakefile`.
3. Open `workflow/scripts/purity_comparisonOOP.py`.
4. Review `config/config.yaml`.
5. Examine the CNB workflow in `CNB_analysis/`.
6. Check the manifest structure and required columns.

The key conceptual entry point is the data-cleaning and harmonization logic, because that is where the quality and validity of the final comparison are established.
